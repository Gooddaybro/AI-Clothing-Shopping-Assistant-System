# Assistant Pro v2

Status: implementation contract, 2026-09-11. v1/Lite is unchanged.

## Endpoints and authority

Public authenticated Java endpoints: POST `/api/assistant/v2/chat` and `/api/assistant/v2/chat/stream`.
Public body: message, optional threadId/category/style/season/material/fit/gender/budgetMax and agentMode=pro. No trusted context is accepted from the browser. Pro is feature gated, disabled by default, and never silently falls back to Lite.

Java calls authenticated Python POST `/v2/chat` or `/v2/chat/stream`, with the request schema in `schemas/v2-pro-request.schema.json`. Java prepares history and profile without the Lite demand parser or pre-clarification short circuit. Java binds identity and stores messages. Python understands multiple requirements and chooses tool actions. Runtime credentials never enter model prompts, public events, checkpoints or logs.

## Tool gateway

Python POSTs `/internal/assistant/runs/{runId}/tools/{toolName}` with `X-Internal-Token` and `X-Pro-Run-Token`; body is the tool's arguments object (no wrapper). Java validates both credentials and active run binding before data access. No caller-selected user ID or URL is accepted. Runs bind user/thread/request, expire after ten minutes and are closed after result persistence/error/cancel. Redis holds run data for multi-instance use; unavailable registry fails closed.

Tools and arguments:

- search_products: category/style/season/material/fit/gender/recall_text optional strings, budget_max optional decimal CNY string. At most 20 candidates returned per call, 200 registered SKU pairs per run. Data is an array of snake_case candidate objects with spu_id, sku_id, name, sale_price, color, size, available_stock, main_image_url and optional category/material/fit_type/style_tags/attribute_tags. Only Java-returned pairs are registered.
- get_product_detail: positive integer spu_id. Data object includes spu_id, name, description, main_image_url, min_price, max_price, attributes and optional style_tags/materials/fit_type/category. Price range is not SKU price. This registers the SPU detail, not arbitrary SKU pairs.
- check_availability: positive integer spu_id, nonempty color and size. Resolve SKU then query inventory. Data includes spu_id, sku_id, color, size, sale_price, available_stock; actual pair is registered. Zero stock is success with zero, not a dependency failure.

Python-local tools: search_product_knowledge(query, optional spu_id), search_policy(query), recommend_size(height_cm, weight_kg, optional preferred_fit/spu_id). They use real existing knowledge/rules. Product-specific size claims require actual product-chart evidence; generic rules report basis=generic_rule and their limitation. Local tools cannot register saleable candidates.

All tool results: `status` (ok/empty/needs_input/unavailable/no_evidence/forbidden), `data` (object/array/null), `evidence_id` (string), `source` (java/rag/policy/size), `missing_fields` (string array), `error_code` (nullable string). Unknown arguments are rejected. Monetary values are decimal strings in CNY, no implicit scaling. Examples: 299.90 is below 300.00; 300.01 is not. If adapting integer search budgets, round the recall bound up and precisely filter by the original decimal value.

## Agent actions and constraints

Single-action JSON: tool(kind, tool, arguments); clarify(kind, question); finish(kind, answer, product_refs). Each action may include requirement_updates (requirement_id, status, evidence_ids). Unknown keys/tools are rejected; no generated code executes. Task state retains requirements and hard/soft constraints with source text. Explicit constraints cannot silently weaken. Retrieved instructions are untrusted data.

Tool results drive subsequent actions. Limits start at 12 model decisions, 8 tool attempts, 90 seconds total. Invalid JSON has one repair, temporary dependency failures one retry, all attempts bounded. Successful duplicates are cached except inventory may be refreshed after 15 seconds. HTTP/model timeouts are bounded by remaining deadline. Stop on cancellation, missing essential input, completion or exhausted budget. Partial answers expose unconfirmed requirements; no fabricated success.

## Python final result

`schemas/v2-pro-done.schema.json` defines contract_version, agent_mode, request_id, run_id, thread_id, answer, product_refs, requirements, stop_reason and metrics. Each product ref is spu_id/sku_id/reason, with optional size_advice/basis/evidence_ids. Metrics contain actual decisions/tool_calls/elapsed_ms and nullable token usage. No prices, images or credentials in product_refs. Requirements report id/text/status/evidence_ids; status=pending/satisfied/needs_input/unconfirmed.

Java must validate final pairs against the server-owned run ledger, re-read live facts and match hard filters. New pairs queried during this run are eligible; invented or cross-run pairs are not. A record of Python-supplied IDs alone is not provenance. Java controls public card facts. If price/stock invalidate the result, Java replaces contradictory prose with a safe partial-result explanation as well as removing invalid cards.

## SSE and public result

Python emits zero or more `progress`, optional validated `token`, then exactly one `done` or `error`; data is single-line JSON. progress: run_id, sequence (increasing integer), tool, stage (started/completed), message (server-selected short text). No raw tool data or reasoning. token: content. error: code/message, optionally run_id. Synchronous result equals done.

Java emits `meta` (thread_id, request_id, run_id, agent_mode), progress, optionally token, done/error. It buffers Python answer tokens until final Java validation; progress can stream immediately. Final public done contains thread_id, run_id, agent_mode=pro, answer, recommended_spu_ids, recommended_items, recommendation_status and requirements. Recommended items contain spu_id, sku_id, name, sale_price, main_image_url, color, size, available_stock, reason and optional size_advice/basis; all fact fields come from Java. recommendation_status is STRONG_MATCH/PARTIAL_MATCH/EMPTY/FAILED. No intermediate product cards. Frontend routes cards to existing product detail pages.

Java persists the final validated answer once before sending done, retains final refs through the existing conversation/attribution facilities, and then revokes the run. Disconnect before completion cancels new work and does not persist a partial answer. Unknown/foreign-run progress is dropped; a second terminal event cannot create a second save. Per-run internal state is isolated; conversation facts can be shared between Lite and Pro. Pro Max is not implemented.
