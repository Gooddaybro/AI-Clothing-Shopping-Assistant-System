# Lite / Pro / Pro Max Agent 演进设计

日期：2026-09-10

状态：讨论方案已确认，本文待用户审阅；未授权开始实现。

## 1. 目标与范围

保留现有 Lite 工作流，新增 Pro 动态工具调度执行引擎。Pro 能理解一句话中的多个需求，根据工具返回结果调整下一步行动，并展示真实商品卡片。Pro Max 是后续多 Agent 协作方向，本期不实现。

新增执行引擎，不复制整个项目。共享业务查询、知识检索、事实校验和前端商品组件；必要时增加工具适配层，避免改变 Lite 行为。

| 模式 | 需求理解与调度 | 定位 |
| --- | --- | --- |
| Lite | 保留 Java 主导的规范意图与现有 Python 条件工作流 | 稳定基线、明确需求 |
| Pro | Python LLM 理解多个需求，根据工具结果逐步决策 | 复合需求、动态调整 |
| Pro Max | 未来由协调 Agent 分配专业任务并汇总 | 验证存在协作收益后再建设 |

多 Agent 不预设为更准确或更快。应依据任务完成率与成本决定是否引入。

## 2. 已核实的代码基础

- `clothing_assistant/agent/router.py`：优先采用 Java demand-intent-v2/v3 规范任务，否则执行规则路由。
- `clothing_assistant/agent/langgraph_executor.py`：已有 LangGraph 条件图、工具预算、回答校验与重试路径。
- `clothing_assistant/agent/tool_registry.py`：现有 ToolSpec 使用 should_run 规则选择工具，可复用底层执行能力。
- `clothing_assistant/tools/size_tool.py`、`rag_tool.py`、`policy_tool.py`：已有尺码、知识与政策能力。政策无来源时已有明确兜底。
- Java `InternalProductController`：已有 `/internal/products/search`、`/internal/products/{spuId}`、`/internal/skus/search`、`/internal/recommendation-candidates`。
- Java `InternalInventoryController`：已有 `/internal/inventory`。

以上仅确认入口和部分实现存在，不代表接口字段、鉴权或端到端能力已验证。Python 的本地商品目录不能作为 Pro 生产价格、库存的权威来源。

## 3. 职责边界

Java 负责身份验证、用户归属、业务授权、真实商品与库存数据、会话持久化、前端入口和最终商品数据组装。

Python Pro 负责理解原始问题、拆解需求、维护约束和完成情况、选择工具及参数、依据结果调整行动、生成有证据的回答。

扩大的是 Python 的调度自主权，不扩大用户的数据访问权限。服务端绑定身份和授权上下文；模型不能通过填写 userId 改变访问对象，也不能任意指定网络地址执行查询。

Lite 保留现有意图链路。Pro 不将 Java 的单个主意图作为强制路由。Java 可以提供可信业务上下文，但不能按旧版单意图提前锁死 Pro 可查询的商品范围。

## 4. 模式入口与会话

输入框附近提供 Lite / Pro 选择，第一版默认 Lite，不自动升级。Pro Max 暂不开放可用入口。

每条消息发送时固定本轮模式，下一轮可以切换。模式由 Java 校验后传给 Python。建议新增模式字段，缺省保持 Lite，最终字段命名在接口契约核实时确定。

两个模式使用同一套持久化历史和已确认用户偏好，但内部执行状态隔离。本轮工具结果按 run 标识归属，不能因切换模式把过期库存当作当前事实。

## 5. Pro 决策循环

采用单 Agent 逐步决策和需求清单，不要求预先生成不可调整的长计划。继续使用 LangGraph 承载固定循环骨架；工具选择、顺序和结束时机由模型结合结果决定。

执行过程：准备可信上下文 → LLM 决策 → 参数及权限检查 → 工具执行 → 记录结果 → 再次决策。需要追问时结束本轮；提交答案时进入确定性校验和最终输出。

模型只选择三类行动：调用已注册工具、向用户追问、提交最终答案。追问和回答不属于业务查询工具。

状态保存：

- 原始需求、硬性约束、软偏好及其来源。
- 已知条件，例如身体数据和当前引用商品。
- 需求清单，分别标记待处理、已满足、缺少信息、无法确认。
- 工具执行记录、候选商品及对应证据来源。
- 已消耗预算、失败和停止原因。

用户约束不得静默放宽。例如无 300 元以内商品时可以换查询表达，但改成 500 元预算需要用户明确同意。“能退换”作为要求时，缺少政策证据不能判定该要求已满足。

## 6. 第一版工具清单

以下为建议工具名，不表示已有同名实现。

| 工具 | 责任 | 实现基础 |
| --- | --- | --- |
| search_products | 按明确约束检索候选 | Java 推荐候选/搜索接口，核实筛选字段 |
| get_product_detail | 读取商品属性、价格及规格 | Java 商品详情，核实价格与规格字段 |
| check_availability | 确认商品指定颜色、尺码的库存 | 封装 Java SKU 查询和库存查询 |
| recommend_size | 根据身体数据、偏好和商品尺码依据给建议 | 适配现有 Python 尺码能力 |
| search_product_knowledge | 检索面料、养护、搭配等知识 | 适配现有 RAG，保留来源和商品适用范围 |
| search_policy | 查找适用的退换、物流政策 | 适配政策检索；无有效来源则无法确认 |

价格先随详情提供，不单独拆工具。SKU 定位与库存查询属于确定性步骤，封装在一个工具中。通用尺码规则不能包装成特定商品的尺码表；缺少商品依据时标注建议限制。

第一版仅包含查询和推荐，不包括购物车修改、下单、支付、退款操作。

工具返回结构至少包含状态、事实数据、来源、缺失字段和可理解的错误类型。必须区分查询成功、无匹配结果、缺少参数、服务失败和无可靠证据。无库存和库存查询超时不能混为一谈。

## 7. Java 与 Python 数据流

Java 初始提供原始问题、会话/运行标识、模式、经过授权的历史与用户资料，以及当前页面商品等可信上下文。偏好保留来源，模型推断不能直接作为已确认用户要求。

Pro 执行过程中可通过受控工具多次查询 Java，包括重新检索候选。每次查询结果关联本轮运行及来源，支持后续商品引用校验。

Python 最终返回文本、选中商品标识、推荐理由、相关尺码建议与证据引用。Java 验证商品来自本轮可信查询结果，补齐卡片数据；前端不从自然语言猜测商品。

运行中新查询到的候选必须进入本轮可引用范围。只校验初始候选会破坏动态换商品能力。该扩展需要在共享契约中明确，不能通过关闭候选校验实现。

## 8. 商品卡片与执行进度

Lite 和 Pro 复用商品卡片组件。卡片展示商品图片、名称、真实价格和详情入口；按实际可用数据附加推荐颜色、尺码、库存查询状态和匹配理由。

LLM 选择真实商品标识并解释推荐，不生成事实价格、图片地址或详情链接。Java 最终组装这些展示字段。库存描述表示查询时状态，不承诺下单时仍有库存。

先展示真实工具事件形成的简短进度，例如“正在筛选商品”“正在确认尺码库存”。最终校验通过后才展示推荐卡片，避免把中间淘汰候选展示成最终推荐。内部推理不展示给用户，详细工具记录进入开发调试视图。

保持现有聊天和流式接口兼容；新增模式、进度事件及商品字段必须先核实当前契约和消费方。不能把新事件直接发给不支持它的旧客户端。

## 9. 终止、降级与校验

- 信息已足够时立即结束，不强制调用全部工具。
- 限制决策步数、工具调用总量、总耗时与重试；预算由服务端配置，模型不能提高上限。
- 相同参数的无效重复调用应阻止；有时效理由的库存复查与短暂失败重试应受预算控制。
- 参数不合法时给出结构化反馈，允许预算内纠正；授权失败不能通过改用户身份重试。
- 缺关键条件时追问并结束本轮，用户回复后从会话中的已确认信息继续。
- 达到预算或依赖失败时，返回已确认信息和未完成项，不伪装为完整成功。
- 最终校验检查商品来源、真实价格、硬性条件和事实依据。修正尝试也计入预算；仍不通过则返回受限结果。

Pro 不静默切成 Lite。若未来需要自动降级，需另行设计用户可见的模式和结果标记。

## 10. 验收与对比

首个完整场景：用户同时提出预算、用途、身体数据、库存和退换要求；Pro 查询商品和尺码，发现无货后切换候选，保留硬性条件，最终逐项回答并展示真实卡片。

必须覆盖：

1. 单需求可少量调用后结束，不为动态而多调用。
2. 多需求不遗漏，工具顺序受返回结果影响。
3. 对应尺码无货后重新选择候选。
4. 无匹配商品时不静默放宽预算等条件。
5. 政策无来源、尺码缺依据时明确限制。
6. 库存超时不被当作无库存，达到预算能输出部分结果。
7. 非法商品标识不能进入卡片；执行中新查询的合法商品可以展示。
8. 跨模式保留会话事实，不混用内部执行状态；Lite 行为兼容。

先以相同问题、上下文和固定工具数据对比 Lite 与 Pro，再用真实接口测试。比较需求完成率、约束满足率、事实准确性、商品卡片正确率、调用次数、耗时与模型成本。记录数据和模型配置，避免库存变化或工具能力差异混淆调度收益。

## 11. 实施顺序与实施前核实项

实施顺序：模式分发与兼容入口 → 共享工具适配 → Pro 决策循环 → 商品来源校验与卡片 → 进度展示和对比评测。本文不构成代码实施指令。

进入实施计划前需要核实的内容：

| 核实项 | 需要形成的结果 |
| --- | --- |
| Java 商品字段和筛选能力 | 确定工具参数、价格/图片/规格映射及必要接口扩展 |
| 内部接口鉴权 | 确定服务身份、授权上下文和调用边界 |
| 商品尺码依据 | 区分商品尺码表与通用规则，确定无法确认的返回方式 |
| 现有商品卡片校验 | 确定本轮动态候选如何登记和校验 |
| 现有 SSE 与聊天协议 | 确定模式、进度、结果字段及兼容方案 |
| 预算初值 | 通过典型复合需求试运行确定步数、耗时和重试配置 |
| 共享契约文件 | 当前工作区未找到 AGENTS.md 引用的共享规则文档；实现前定位并核对，不臆测内容 |

这些是实现前证据核实项，不改变本文已确定的产品范围与职责边界。

## 12. Pro Max 演进条件

当评测显示单 Agent 存在明确的专业分工或独立审查需求，再设计协调者与专业 Agent。沿用共享工具、身份授权、事实校验和商品输出能力；不提前搭建完整多 Agent 框架。
